# 0.0.1 staging 候选

本版整合 V2 游戏执行、历史功能退役及全仓清理。前后端版本为 0.0.1，staging 从活动 release 的完整 SHA 发布，候选标签为 v0.0.1-rc.1。

目标为 `mysql.testhut.top:13306/aisocialgame`。发布前导出的结构有 31 张表；当前结构需 51 张表，另补齐 6 列、5 个索引并将房间状态改为 VARCHAR。执行顺序如下，各文件从 backend/sql 起算：

1. `schema.sql`：为缺少的表创建当前结构，现有表继续由增量处理。
2. `20261008_room_lifecycle.sql`：房间状态、房间号、等待时间和过期状态。
3. `20261031_staging_v0_0_1.sql`：来源字段、策略发布关联及相应索引。
4. `20261004_admin_emergency_codes.sql`：现行紧急码结构及一次性历史认证材料退役，现有 TOTP 和完整会话保留。
5. `20261029_retire_credit_holds.sql`：确认旧占额列已退役。
6. `releases/0.0.1/staging-history.sql`：清除已核对的旧游戏及从属记录、旧角色记忆和旧 token 流水。

staging 已有的 `idx_rooms_game_status_created(game_id,status,created_at)` 查询索引继续保留；验证同时要求当前快照的全部列与索引存在，以及该历史索引完整保留。

历史 SQL 保持原字节。通过现有数据库控制台逐批执行，使用平台执行 ID 记录进度，不新增项目迁移账本或自动执行链。实际删除前停止旧 staging 实例，重新固定候选 ID、数量及资金基线；本轮不操作其他环境。

历史清理的已核对基线没有回放、实验室数据或 V2 旧记忆片段。若再次核对发现这些数据，先核对其关联关系再继续相应批次。结构变更可能部分提交，失败后查询原执行记录并向前修复；恢复旧制品前须核对数据库兼容性。清理不改变账户余额，真实 AI 验收的实扣与未知费用另记。

交付记录包含候选 SHA、发布 ID、配置身份、SQL 执行 ID、实际删除数量、L2／原生 MySQL／L4 结果及分支收尾。当前 local 服务保持运行。
